# Comments

The depth behind `What does not belong in user-facing docs` in `SKILL.md`:
which comment syntax carries which kind of note, and when saying nothing
beats saying something. Fragments are fenced `rust,ignore`.

## Doc comments say something new

A comment earns its place by adding information the reader cannot get from the
code next to it. Do not teach language basics in a comment (what `?` does, that
a `match` must be exhaustive); the reader of Rust knows them, and the comment
rots into noise. A doc comment that only restates the item name or signature
is worse than none, since it looks like documentation and hides the gap:

```rust,ignore
/// Gets the length.
pub fn len(&self) -> usize { /* ... */ }
```

Where the honest content is nothing, either leave the item undocumented, or,
in a crate that warns on `missing_docs`, put a local `#[allow(missing_docs)]`
on it. Do not write filler to quiet the lint. The same goes for enum variants
whose names already say everything.

## Two comment forms, two audiences

`///` and `//!` are for people who use the crate: they render. `//` is for
people who edit it: implementation notes, TODOs, and code disabled for now.
Leave commented-out code out of committed work when version control can hold
it, but if it must stay, `//` is the only form it may take, never a doc line.

A single item may carry both. A work-in-progress note sits under the doc
comment as a plain comment, so it stays out of the rendered page:

```rust
/// Returns the display label for the account.
// TODO: cache the formatted label once names become immutable.
pub fn label(name: &str) -> String {
    format!("account:{name}")
}
```

## Write docs by hand

Prefer a plain doc comment over docs generated by a macro. Generated text
cannot be reviewed where it is written, is invisible to a reader of the source,
and drifts from the item it describes. Reach for generation only when the same
text truly must repeat verbatim across many items, and keep the macro-produced
part as small as possible.
